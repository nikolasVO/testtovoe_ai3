## Обязательные сценарии

Все четыре сценария из задания прошли на PostgreSQL и проверяются также через настоящий HTTP:

1. 20 одновременных одинаковых платежей дают одно начисление.
2. 10 одновременных отказов последней ноги дают один возврат.
3. Отказ первой ноги приводит к успеху второй; в истории две попытки.
4. Поздний результат после сторожа отклоняется; задача не получает одновременно результат и возврат.

## Воспроизведение

```bash
cp .env.example .env
docker compose up --build -d --wait
make lint
make test
make e2e
```

`make test` работает в отдельной тестовой базе и не очищает основную. E2E добавляют изолированных демонстрационных пользователей в основную локальную базу. Стандартный таймаут провайдера — 60 секунд.

Для ускоренного прогона в отдельном окружении:

```bash
PROVIDER_TIMEOUT=6 HTTP_TIMEOUT=1 LEASE_SECONDS=3 make e2e
```

Сохранённые журналы фактического прогона: [unit/integration](docs/verification/docker-tests.log), [E2E](docs/verification/docker-e2e.log).

GitHub Actions повторяет проверки при push и pull request. Локальный успешный прогон не означает автоматического успеха CI: статус конкретного запуска смотрите во вкладке Actions репозитория.

Файлы `pytest.txt`, `pytest.xml` и `schema-offline.sql` в `docs/verification` относятся к предварительным проверкам; офлайн SQL не является свидетельством выполнения миграций. Скриншоты в `docs/previews` сняты с тестовыми ответами API и показывают только интерфейс.
