# Generation Orchestrator

Сервис принимает заказ на генерацию, списывает токены и передаёт задачу первой подходящей ноге провайдера. При отказе пробует следующую, а если вариантов больше нет — возвращает токены ровно один раз.

**Python 3.12 · FastAPI · PostgreSQL 17 · Docker Compose · 4 API-процесса**

## Быстрый запуск

Нужны Docker Engine / Docker Desktop и Docker Compose v2.

```bash
git clone https://github.com/nikolasVO/testtovoe_ai3.git
cd testtovoe_ai3
cp .env.example .env
docker compose up --build -d --wait
```

Compose запускает PostgreSQL, применяет миграции, поднимает API в четырёх процессах и двух фейковых провайдеров. Пользователь `1` получает 100 токенов через запись в журнале; повторный запуск их не начисляет.

| Адрес | Назначение |
|---|---|
| [localhost:8000/docs](http://localhost:8000/docs) | Swagger / OpenAPI |
| [localhost:8000/demo](http://localhost:8000/demo) | Демопанель сценариев отказа |
| [localhost:8000/health/ready](http://localhost:8000/health/ready) | Готовность БД и миграций |
| [localhost:8001/docs](http://localhost:8001/docs), [localhost:8002/docs](http://localhost:8002/docs) | Alpha и Beta |

## API

| Запрос | Назначение |
|---|---|
| `POST /generate` | Списать цену и создать задачу |
| `POST /webhooks/providers/{name}` | Принять результат провайдера |
| `POST /webhooks/payments` | Начислить токены по успешной оплате |
| `GET /tasks/{id}` | Статус, текущая нога и история попыток |
| `GET /users/{id}/balance` | Баланс, сумма журнала и последние операции |

```bash
curl -s -X POST http://localhost:8000/generate \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: example-request-1' \
  -d '{"user_id":1,"model_slug":"image-fast","prompt":"A mountain lake","ref_images":[]}'

# Подставьте task_id из ответа:
curl -s http://localhost:8000/tasks/TASK_ID
```

Ответ генерации — `202 {"task_id":"uuid","replayed":false}`. Нет подходящей ноги — `400` до списания; недостаточно токенов — `402`; уже три активные задачи — `429`. Необязательный `Idempotency-Key` защищает от повторного списания при повторе того же заказа.

Вебхуки обоих типов подписываются: `X-Signature` — hex HMAC-SHA256 сырых байтов тела с `WEBHOOK_SECRET`. Платёж начисляется только при `status=succeeded`; повтор одного `payment_id` не создаёт нового начисления. Форматы запросов и дополнительные ответы описаны в Swagger и [справочнике](docs/reference.md).

### Каталог и переходы

| Модель | Цена | Ноги по приоритету |
|---|---:|---|
| `image-fast` | 2 | Alpha: до 4 референсов → Beta: до 10 |
| `video-long` | 25 | Beta: до 2 → Alpha: до 1, `skip_on_moderation=true` |

`technical`, синхронный 5xx и таймаут ведут к следующей подходящей ноге. После `moderation` пропускаются ноги с `skip_on_moderation`; `payload` сразу завершает задачу с возвратом. Если ноги закончились, задача получает `failed` и один возврат.

Фейковые провайдеры отвечают `202`, затем через 2–20 секунд присылают подписанный результат. Можно настроить отказы, дубликаты, отсутствие и задержку вебхука — [параметры провайдеров](docs/reference.md#настройка-фейковых-провайдеров).

## Почему деньги двигаются ровно один раз

Приём заказа, списание, создание попытки и запись в outbox выполняются одной транзакцией PostgreSQL. Начисление платежа и окончательный отказ с возвратом также фиксируются атомарно.

- Строка пользователя блокируется на время проверки баланса, лимита активных задач и финансового перехода.
- Уникальные ограничения защищают `payment_id` и пару `(task_id, kind)` от повторного начисления, списания или возврата между процессами.
- Баланс изменяет только `AFTER INSERT`-триггер журнала. Журнал запрещает изменение и удаление записей.
- Отложенные constraint triggers проверяют равенство баланса сумме журнала и соответствие проводок состоянию задачи/платежа перед коммитом.

Обработчики отправки используют сохранённый outbox, `FOR UPDATE SKIP LOCKED`, lease и token владельца. Сторож и вебхуки повторно проверяют состояние под блокировками. Бизнес-состояние хранится в БД; сетевые запросы выполняются вне транзакций.

## Падение процесса и поздний результат

| Момент сбоя | Что происходит |
|---|---|
| До коммита вебхука | Транзакция откатывается; повторная доставка выполнит операцию |
| После коммита, до HTTP-ответа | Повтор обнаружит уже выполненную операцию без нового движения токенов |
| После списания, до отправки | Другой обработчик заберёт сохранённый outbox |
| Провайдер принял запрос, но ответ не сохранён | После истечения lease повторяется тот же `attempt_id`; провайдер возвращает прежний job |

Сторож считает попытку неудачной после `PROVIDER_TIMEOUT` (по умолчанию **60 секунд**) и вызывает тот же переход, что отказ провайдера: следующая нога или окончательный возврат.

**Поздний `completed` отклоняется**, если дедлайн истёк или попытка уже закрыта/заменена. Вебхук получает `200` с отметкой `ignored_late` / `ignored_terminal`; результат не выдаётся, задача не возобновляется, возврат не отменяется. Так пользователь не получает одновременно результат и возврат. Цена этой политики — провайдер мог выполнить работу, результат которой уже не будет принят.

## Проверки

```bash
make test       # unit + PostgreSQL integration, отдельная test-db
make e2e        # HTTP, четыре API-процесса и оба провайдера
make lint       # Ruff
```

Локально прошли **103 модульных и интеграционных теста + 12 E2E**, включая все четыре обязательных сценария:

1. 20 одинаковых одновременных оплат → одно начисление.
2. 10 одновременных отказов последней ноги → один возврат.
3. Отказ первой ноги → успех второй, две попытки в истории.
4. Поздний результат после сторожа → отклонение без повторного финансового эффекта.

Дополнительно проверяются гонки обработчиков, восстановление после `SIGKILL` и финансовые инварианты через Hypothesis. Интеграционные тесты не очищают основную БД; E2E создают изолированных демонстрационных пользователей. GitHub Actions запускает эти проверки при push и pull request.

## Миграции

При запуске Compose миграции выполняет отдельный сервис `migrate` до старта API. Повторное применение и создание следующей миграции:

```bash
docker compose run --rm migrate

docker compose run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD:/srv" api alembic revision -m 'add provider routing metadata'
# Заполните upgrade()/downgrade() в migrations/versions/ — используется явный SQL.
docker compose build
docker compose run --rm migrate
```
