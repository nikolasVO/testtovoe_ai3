# ADR 003 — Границы guarantees и проверяемые допущения

**Статус:** принято.

1. Exactly-once относится к финансовому эффекту в PostgreSQL. Количество доставок вебхука и HTTP POST не обещано равным одному.
2. Eventual completion/refund требует доступности БД и хотя бы одного работающего процесса. Во время полной остановки ничего не «исполняется в памяти другого сервиса»; работа остаётся сохранённой до рестарта.
3. Неопределённый POST может реально создать задание у провайдера. Встроенные симуляторы дедуплицируют по attempt ID. Для настоящего провайдера без такой поддержки нельзя обещать один внешний job.
4. `attempt_id` передаётся и возвращается в provider API как явное расширение контракта. Это необходимая корреляция раннего callback и восстановления после сбоя.
5. Отправитель платежного вебхука должен повторять запрос без успешного подтверждения. Оркестратор не может восстановить событие, которое никогда до него не дошло.
6. Секрет общий по условию тестового. В production отдельно разделяются доверие к провайдерам генерации и право начислять средства.
7. Пользовательская авторизация исключена ТЗ. Demo/admin ограничены отдельным ключом и локальными портами; это не публичный multi-tenant perimeter.
8. SQL-триггеры защищают обычные операции и регрессии, но владелец/суперпользователь БД технически может отключить их. Production runtime role должен быть отдельным и ограниченным.
9. Тесты на SQLite не заменяют проверки row locks, deferred triggers и SKIP LOCKED. Поэтому интеграционные сценарии требуют PostgreSQL и честно пропускаются без явно настроенной тестовой БД.
10. Наличие тестового кода не является доказательством успешного прогона. Фактически выполненные проверки и недоступные проверки перечисляются в VERIFICATION.md.
