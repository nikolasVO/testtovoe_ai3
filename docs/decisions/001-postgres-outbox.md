# ADR 001 — Одна транзакционная граница и PostgreSQL outbox

**Статус:** принято.

## Проблема

Четыре процесса одновременно принимают оплату, заказы и callback. Списание, сохранение задания и отправку внешнего HTTP нельзя атомарно объединить обычной SQL-транзакцией. Process-local lock, set с payment IDs и background task не переживают рестарт и не синхронизируют процессы.

## Решение

Списание, task, attempt и outbox сохраняются одним коммитом. Изменения пользователя сериализуются его row lock. Финансовые события уникальны по бизнес-идентификатору. AFTER INSERT trigger — единственная обычная точка изменения баланса, deferred constraints сверяют финальное состояние.

Outbox получает кратковременный lease и fencing token. При отправке не удерживаются row locks. После восстановления используется прежний attempt ID. Фейковые провайдеры поддерживают его как idempotency key и хранят принятые задания в БД.

Общий порядок write locks: user → task → attempt → outbox. Claim очереди — отдельная завершённая транзакция без последующего user lock внутри неё. Watchdog сначала блокирует user с SKIP LOCKED.

## Последствия

Финансовый эффект exactly-once внутри одной БД достижим без распределённой транзакции. HTTP остаётся at-least-once. БД выполняет также роль очереди: есть polling и дополнительная нагрузка, но для небольшого сервиса это осознанная плата за простой эксплуатационный контур.

Полная проверка сумм на commit не предназначена для бесконечного журнала высокого TPS. Она оставлена как явная защита инварианта тестового; при масштабировании нужна более дешёвая контролируемая запись и независимая сверка.
